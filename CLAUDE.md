# Fueling Calculator — Claude notes

## Stack

Vanilla JS, no build step. Four files that matter:

| File | Role |
|------|------|
| `data.js` | All storage: Supabase reads/writes, localStorage, ID generation, plan math |
| `app.js` | All UI: rendering, event handlers, navigation state |
| `export.js` | Clipboard/text export logic |
| `style.css` | Design tokens + all component styles |

`index.html` is a static shell — all dynamic content is injected by `app.js`.

## Data layer

Events live exclusively in Supabase (fetched fresh on every `getEvent` call via `dbToEvent`). There is no localStorage event cache.

**Two things** do live in localStorage only:
- Execution plans — keyed `fuelPlanner.execPlan.{segId}` — synced to `segments.execution_plan` via `saveExecutionPlan`
- Default exec interval — `fuelPlanner.defaultExecInterval`

Per-segment overrides (`execInterval`, `execPlan`) are written to the DB via direct PATCH on the segment row. Any new per-segment field needs both sides: `dbToEvent` (read) and `eventToDb` + the `save_event` RPC (write). New DB columns require a migration in `migrations/`.

## Rendering pattern

Full re-render: `renderDetail()` — re-fetches the event from Supabase and re-renders the whole detail view. Used after saves that change multiple things.

Partial re-render: `segEl.outerHTML = segmentSectionHTML(seg, multiSeg)` followed by `reattachSegmentHandlers(segId)` — used after fast local changes (stepper, inline edit) to avoid a round-trip.

Inline editing uses `makeEditable(el, onSave)` + `handleInlineEdit(el, eventId)`. To add a new editable field: add `data-inline="field-name"` to the span, add a case to `handleInlineEdit`, and normalise `el.textContent` before `makeEditable` runs if the display format differs from the edit format (see how `seg-duration` and `exec-interval` do it).

## Execution plan

Generated by `Data.generateExecutionPlan(segment)`. Reads `segment.execInterval` (or `getDefaultExecInterval()`) for slot spacing. Stored per-segment in both localStorage and Supabase. Staleness is detected in `executionPlanHTML` by comparing slot count and interval against the stored plan.

## Running tests

```bash
node tests/data.test.js
node tests/export.test.js
```

No npm install needed. One pre-existing test failure (`distributes 4 gels evenly…`) is a known off-by-one in the assertion, not in the implementation.
